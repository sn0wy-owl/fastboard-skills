# Приёмка И Доказательства

## Четыре Независимых Проверки

| Слой | Что подтверждает | Чего не подтверждает |
|---|---|---|
| Offline checker | структура, id, слои, ссылки, переменные, явные ошибки SQL-слотов | данные сервера, внешний вид, клики |
| Живой SQL smoke | действующие поля/агрегаты, эталонные числа | native WHERE с клика, popup UX |
| Server readback | сервер сохранил текущие настройки | правильный рендер и хороший дизайн |
| Browser QA | реальное взаимодействие, подписи и композиция | полную корректность незатронутых данных |

Не смешивай эти доказательства в одно «валидатор прошёл».

## Минимальные Сценарии

1. Весь портфель: эталонное число инициатив и задач, сумма непересекающихся групп.
2. Ведомство: ожидаемый subset, пересчёт всех блоков страницы, правильные числители/знаменатели.
3. Дата: выбран именно тот тип даты, который написан на фильтре; границы диапазона включены/исключены по согласованному правилу.
4. Пустой subset: нули/понятное пустое состояние, не SQL exception и не старые данные.
5. Одна инициатива A: заголовок popup совпадает с реестром, задачи принадлежат её id, количество совпадает.
6. Закрытие и B: другой набор, без примеси A. Повторное B не должно закрывать popup через ошибочный invert.
7. Самая нижняя доступная строка реестра: видны заголовок, закрытие и таблица popup; доступны оставшиеся строки.
8. Возврат назад: нужная страница, ожидаемое сохранение/сброс фильтров, отсутствие лишнего промежуточного экрана.
9. Клик по каждой карточке и кнопке: верхние вкладки FB не заменяют этот тест.
10. Pie/bar: корректные единицы, все нужные подписи и легенды, top-N действительно отсортирован и ограничен.

Если обещана мобильная версия, проверь её в **FB**, не только в HTML. У fixed-width доски могут быть собственные механизмы масштабирования, отличные от CSS responsive.

## Smoke И Возобновление

Для каждого виджета с isRealData:

- возьми актуальный FROM/alias модели;
- выполни его переменные/разрезы/показатели с правильными WHERE/GROUP/ORDER/LIMIT;
- проверь ожидаемые числа, строки и пустые случаи;
- при сложном SQL используй фактический native-запрос из браузера, а не упрощённый regex-сборщик;
- включи скрытые таблицы и динамические подписи popup.

Хэш возобновления должен включать SQL, projectId, modelId, scenario/filter, актуальность источника или snapshot. В одной итерации можно повторно использовать неизменённый запрос на неизменённых данных, но не переносить его PASS через неизвестную перезагрузку ETL.
Rate limit помечается как rate_limited/pending, не как пустые данные. Жди по политике сервера с конечным числом попыток; не бомби endpoint.
Обычный REST допускается при действующей авторизованной сессии пользователя, не с PAT вместо JWT и не для обхода запрета доступа. Не сохраняй Cookie/X-Auth-Token в артефакты.

## Readback

Для **каждой** страницы сравни:

- id/имя/геометрию страницы, переменные и стартовые значения;
- полный набор id виджетов и фильтров;
- dataSettings, sqlData, events, positionConfig;
- критичные viewSettings, палитры и порядок layers;
- активную тему и реальные цветовые ссылки.

Ответ «Ok» при save — не readback. Если сервер нормализовал поле, различие должно быть объяснено, а не проигнорировано.

## Негативные Тесты

Встроенный selftest проверяет отказ на дубликате id, пропавшем слое, несуществующей переменной, конфликте goTo/transition, пустом шаблоне KPI, выходе за доску, чужой модели и мёртвом цвете.
Для собственного валидатора добавь аналогичный намеренный дефект. Нулевые нарушения без контрастного прогона — слабое доказательство.

## Консилиум

Четыре роли ниже — памятка вопросов, а не машиночитаемая проверка: вердикт нельзя повторить
командой. Обязательная часть приёмки — прогон `scripts/check-dashboard.cjs`, реальные SQL всех
виджетов и браузерный проход; вывод ролей идёт в отчёт как мнение проверяющего.

**Критик:** все ли подписи/легенды/закрытия читаются, нет ли пустых растянутых блоков?

**Стратег:** сохранён ли одобренный UX, главная ли это управленческая панель, а не случайная коллекция графиков?

**Аналитик:** зерно/дедупликация/статусы/знаменатели/сценарии соответствуют источнику?

**Креатор:** остались ли реальные native-графики, единая типографика/палитра/сетка, насколько близко к согласованному HTML?

Критичные дефекты исправляются до сдачи. Нативную косметику не превращай в бесконечный рефакторинг, но перечисли отличия.

## Формат Отчёта

```json
{
  "status":"PASS|FAIL|PARTIAL",
  "buildFingerprint":"HASH",
  "datasetSnapshot":"KNOWN_VERSION_OR_UNKNOWN",
  "structure":{"pages":4,"errors":0},
  "widgets":[{"pageId":"ID","widgetId":"ID","queryHash":"HASH","status":"PASS","actualRows":5}],
  "scenarios":[{"name":"department","expected":6,"actual":6,"status":"PASS"}],
  "readback":[{"pageId":"ID","status":"PASS"}],
  "browser":[{"scenario":"A_then_B","status":"PASS","evidence":"LOCAL_SCREENSHOT"}],
  "knownDifferences":["page-local filters","native selection chip remains after close"]
}
```

Значения в примере иллюстративные. Не заполняй PASS заранее.

## Передача Пользователю

```text
Собрано: ссылка на главный экран.
Страницы: названия. Навигация: главная → группа → popup.
Данные: источник и контрольные числа; demo/production.
Проверка: SQL, сценарии, readback, browser, краткий вердикт четырёх ролей.
Особенности: scope фильтров, способ сброса выбора, native-отличия от HTML.
Артефакты: сборщик и отчёт, команды воспроизведения без секретов.
```
